# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ToyBox — a full-stack e-commerce demo: React 18 + Vite + TypeScript frontend, FastAPI + SQLAlchemy 2.x + SQLite backend, Stripe Checkout (test mode) for payments. Checkout requires a signed-in, approved account. See `README.md` for the full architecture diagram, database schema, API contract table, and design notes ("browser is never trusted with money", stock decrements exactly once, order lines are frozen snapshots) — read it before making payment or pricing changes.

## Commands

### Backend (run from `backend/`)
```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
alembic upgrade head                                 # apply migrations — required after pulling new model changes
python -m scripts.seed                               # catalogue + synthetic 2026 order history
uvicorn app.main:app --reload --port 8000
```
- `python -m scripts.seed --reset` — drop and recreate every table first
- `alembic revision --autogenerate -m "..."` — create a new migration after changing a model; always inspect the generated file before applying
- `pytest` or `python -m pytest -v` — run all tests; `pytest tests/test_checkout.py -v` for one file, `pytest tests/test_checkout.py::test_name -v` for one test. Each test gets its own throwaway SQLite file. `tests/conftest.py` forces `SMTP_HOST`, `ADMIN_NOTIFY_EMAIL`, `LYZR_API_KEY` and `LYZR_AGENT_ID` to blank before the app loads, because pydantic reads the real `backend/.env` and tests that register users were once sending ~50 real emails to the admin address. Never remove that guard.

### Frontend (run from `frontend/`)
```bash
npm install
npm run dev         # http://localhost:5173
npm run build        # tsc -b && vite build
npm run typecheck    # tsc --noEmit, no build output
node --test          # pure chat logic tests (Node 24, no packages); plain `node --test`, give it no directory argument
```
No lint script and no npm test script; the pure chat logic is tested with `node --test` run from `frontend/` (see Chatbot).

### Both at once
- `.\scripts\start.ps1` / `.\scripts\stop.ps1` (Windows) — background uvicorn + vite, PID-tracked in `scripts/.pids/`, logs in `scripts/logs/`; polls `/health` until the backend responds before returning.
- Gotchas: (1) `backend/.env` is read only when uvicorn starts, so restart the backend after editing it (a stale process once sent the admin notice to the fallback `admin@example.com` because `ADMIN_NOTIFY_EMAIL` was set after startup). (2) Environment variables beat `.env`, and `start.ps1` inherits them from the PowerShell window; a leftover `DATABASE_URL`, `SMTP_HOST` or `ADMIN_NOTIFY_EMAIL` from an earlier test session once pointed the app at a copy database with email off. Clear them (`Remove-Item Env:DATABASE_URL, Env:SMTP_HOST, Env:ADMIN_NOTIFY_EMAIL, Env:LYZR_API_KEY, Env:LYZR_AGENT_ID -ErrorAction SilentlyContinue`) or use a fresh terminal. (3) `start.ps1` warning "Backend did not report healthy within 45s" is only a slow cold start; check `http://localhost:8000/health` and `scripts/logs/backend.err.log`. (4) `start.ps1`/`stop.ps1` also start/stop the Cloudflare tunnel container, so a restart briefly takes the public site down.
- `docker compose up --build` — same stack containerized; migrations run automatically on backend start; SQLite + uploads persist on named volumes.

### Reset Data (standing phrase)
When Vishal says "Reset Data", run `python -m scripts.reset_data --yes` from `backend/`. Do not ask for confirmation; the phrase is the authorization. It first copies the database to `C:\Users\visha\ToyBox-backups\app-YYYYMMDD-HHMMSS.db`, then deletes all customer users (including pending and rejected registrations), all orders, order items, payments and cart items, and the revoked tokens of the deleted users. Stock from deleted paid/shipped/delivered orders is added back. The admin account and the catalogue (products, images, categories) are kept. Afterwards report the before/after counts and the backup path. Without `--yes` it is a dry run that only previews the counts. Guards: it only works on a SQLite database with `ENVIRONMENT=development` and refuses (exit 2) if no admin exists. If SQLite reports "database is locked", stop the stack (`.\scripts\stop.ps1`) and retry.

### Stripe webhook testing
`stripe listen --forward-to localhost:8000/api/webhooks/stripe`, then copy the printed `whsec_...` into `backend/.env` as `STRIPE_WEBHOOK_SECRET` and restart uvicorn. Test card `4242 4242 4242 4242`. With `STRIPE_SECRET_KEY` blank and `ALLOW_DEV_PAYMENT=true`, checkout instead calls `POST /api/checkout/dev-confirm/{order_number}`, which runs the exact same confirmation path as the real webhook — use this for local iteration without any Stripe setup at all.

## Architecture

### Checkout (login required)
`routers/checkout.py: create_checkout_session` builds a *pending* order from the server-side cart, then either hands back a Stripe Checkout URL or, in dev mode, a synthetic confirm URL. The order is **not** marked paid here. Only the signature-verified webhook (`checkout.session.completed`) or `dev-confirm` calls `order_service.mark_order_paid`, which decrements stock and is idempotent — it refuses to run twice on the same order. There is no guest checkout: logged-out visitors can browse and fill the browser-side cart (`localStorage`, merged into the server cart at login), but `/checkout` sits behind `ProtectedRoute`, which sends them to `/login` and back. Guest checkout (migration `0002_guest_checkout`, endpoint removed) left `orders.user_id` nullable, the billing columns on `orders`, and the card summary columns on `payments`; they are now unused and deliberately not dropped.

### Money and pricing
All money is integer cents everywhere (frontend included — see `lib/format.ts` for the only place cents become a display string). `services/pricing.py: totals_for` is the single source of shipping/tax calculation; never trust a price or total sent from the browser — checkout re-reads `Product.price_cents` from the DB for every line.

### Email
`services/email_service.py` sends the registration emails over real SMTP (Gmail + app password, `SMTP_*` env vars): `send_mail(to, subject, html)` plus three renderers — `render_admin_notice` (new registration waiting), `render_approved` (with the login link) and `render_rejected` (with the admin's reason). `services/registration_service.py` sends them best-effort: a failure, or SMTP being unset (`EmailNotConfigured`), is logged and never fails the request. Recipients and links come from `ADMIN_NOTIFY_EMAIL` (falls back to the first admin user's email) and `FRONTEND_BASE_URL`. No order receipt email is sent; the confirmation page and Orders page are the shopper's record.

### Chatbot
A floating shopper chat widget (`frontend/src/components/ChatWidget.tsx`, mounted in `Layout.tsx`, hidden on `/admin` routes) talks to `POST /api/chat` (`routers/chat.py`), an endpoint that requires a signed-in approved user (anyone else gets `401 not_authenticated` and Lyzr is never called), taking `{message, session_id}` and returning `{reply, products}`. The router calls `services/chat_service.py: ask_agent`, which proxies the message to a Lyzr agent over `httpx`; the Lyzr key (`LYZR_API_KEY`, plus `LYZR_AGENT_ID`) lives only in backend env and never reaches the browser. Messages are capped at 500 characters (`schemas/chat.py`), and an in-memory per-client rate limiter allows 20 requests per minute (`chat_rate_limit_per_minute`). Errors use the usual envelope: `chat_not_configured` (503, keys unset), `chat_unavailable` (503, Lyzr failed, timed out or returned a malformed reply), `rate_limited` (429), plus 422 for validation. Logged-out visitors who click the launcher see a popup with the fixed text in `frontend/src/components/chat/chatGate.ts` (`CHAT_LOGIN_REQUIRED_MESSAGE`) instead of the chat. The widget keeps its session id in `localStorage` under `toybox.chat_session`, but clears it and wipes the conversation on every change of signed-in user (including at page load), so the session no longer survives a reload.

**Product cards:** after the Lyzr call, the router runs `services/chat_products.py: find_mentioned_products` on the reply in a worker thread (`run_in_threadpool`) and returns up to 3 `ChatProduct` items (`schemas/chat.py`: `slug, name, brand, category_name, price_cents, in_stock, min_age_months, max_age_months, image_url`; stock quantity is never sent). Matching: the full product name or the name without a trailing parenthetical, case-insensitive, with curly quotes and en/em dashes folded to plain ones, whole words only (a name inside a longer word does not match); aliases under 6 characters are ignored; the longest match claims its text first; active products only; ordered by first appearance; out-of-stock products are included and flagged. Cards read the live database, so their prices are current even when the answer text quotes the knowledge-base snapshot. A lookup failure is logged with `logger.exception` and returns `products: []`; the reply is never lost.

**Widget structure:** `ChatWidget.tsx` holds state and layout; `frontend/src/components/chat/` holds `ChatMessageBody` (reply renderer), `ProductCard`, `SuggestionChips`, `MessageActions`, and the pure modules `chatText.ts` (reply parser) and `chatSuggestions.ts`. Replies render paragraphs, numbered lists, bullet lists (`-`, `*`, `+`, `•`), `#` headings (shown as bold lines), `**bold**`, `` `inline code` ``, `---` rules (dropped), `[label](target)` links, and bare URLs or site paths; links appear only for http(s) URLs and the site's own routes (an outside link shows its host next to the label, and same-site addresses show as the page path), anything else stays plain text, and nothing is inserted as HTML. Suggestion chips are deterministic (a starter list plus a topic table in `chatSuggestions.ts`; every suggested question is answered by the knowledge base). Each bot message has a copy button and thumbs up/down; thumbs are stored in this browser only, under `toybox.chat_feedback`, and are never sent to the server. "New chat" starts a fresh Lyzr session id. Escape closes the panel, focus moves to the input on open. Nunito is applied only through the `font-chat` class; its Google Fonts stylesheet is requested from fonts.googleapis.com only the first time a visitor opens the chat (injected by `ChatWidget.tsx`), and nothing is requested from Google on other page loads; if Google is blocked or slow, the chat shows in the system sans-serif and still works. The pure logic is tested with plain `node --test` run from `frontend/` (Node 24 type stripping, no packages; give it no directory argument, because naming the directory fails on Node 24): `tests/chatText.test.mjs`, `tests/chatSuggestions.test.mjs` and `tests/chatGate.test.mjs`.

**Confirmed (2026-10-04):** the Lyzr request and response shape in `chat_service.py` (URL, `x-api-key` header, body fields, and reading the reply from `response`; the lines are tagged `# LYZR SHAPE`) matches the sample request from the real Lyzr account, and a live call through `POST /api/chat` returned a correct reply in the `response` field. All 26 questions in `docs/chatbot-kb/test-questions.md` were answered correctly when each was asked in a fresh session (before guest checkout was removed; re-run the list after re-uploading the revised docs). If Lyzr changes its API, the tagged lines are the only place to edit.

The knowledge pack the agent is trained on is `docs/chatbot-kb/` (docs `00`-`02` and `04`-`08`, a generated `products.md`, and the `test-questions.md` golden list). To refresh product data, run `python -m scripts.export_kb_products [--base-url URL]` from `backend/` and re-upload the files to Lyzr, chunking by heading. The committed `products.md` has `localhost` links, so pass the public site URL as `--base-url` when exporting for a deployed site. `docs/chatbot-kb/_crawl/` is raw crawl scratch and is not ingested.

**Feedback page dependency:** the knowledge pack (docs 00, 06, 07, 08) and the agent prompt send shoppers to the Feedback page when the bot cannot help. The `/feedback` route, the header link, `FeedbackPage.tsx` and `VITE_N8N_FEEDBACK_FORM_URL` are on this branch because it was cut from `feat/larger-checkout-pages`. Merging this branch to `main` without that branch's commits would make those answers lead to the 404 page, so merge `feat/larger-checkout-pages` first.

Before deploying (not implemented yet): do NOT set `FORWARDED_ALLOW_IPS=*` or `--forwarded-allow-ips='*'`. In the pinned uvicorn 0.32.1, `*` makes `request.client.host` the left-most `X-Forwarded-For` entry, which the client supplies, so unless Render's edge strips an incoming `X-Forwarded-For` a caller can send a fresh value on every request and get a new limiter key each time, bypassing the paid-API cap and growing the limiter's in-memory dict without bound. Without trusting the proxy, every visitor shares one key and one global 20-per-minute cap. Pre-deploy work (recommended, not done): since chat is now authenticated, preferably key the limiter on the user id (a one-line change in `routers/chat.py`), which also removes the `X-Forwarded-For` spoofing concern. Otherwise key the limiter on the right-most `X-Forwarded-For` entry (the hop the platform appended) through a small helper in `routers/chat.py`, or set `forwarded-allow-ips` to the platform's actual proxy range; after deploying, send a forged `X-Forwarded-For` and check the resolved key; add a global per-minute and per-day ceiling or a Lyzr-side spend cap; evict empty limiter keys and consider keying IPv6 clients by /64. Known limitation: the whole site, and therefore the chat call, needs `localStorage` to be available, because the shared axios request interceptor reads it unguarded. Security: the login page no longer shows the seeded demo logins (they were removed, as were the passwords in the README); they must never go into the chatbot knowledge base.

### Auth
JWT access token (30 min) + refresh token (7 days); the Axios interceptor in `api/client.ts` retries a 401 once after silently refreshing. Logout adds the refresh token's `jti` to a `revoked_tokens` denylist rather than trying to invalidate the JWT itself. `role` (`customer`/`admin`) gates every `/api/admin/*` route via `get_current_admin` in `core/deps.py`.

**Registration approval:** `users.approval_status` is `pending` / `approved` / `rejected` (plus `rejection_reason`, `reviewed_at`). `POST /api/auth/register` creates a `pending` account and returns `{status: "pending", message}` with no tokens and no auto sign-in, so there is no cart merge at registration (the guest cart merges at the first login after approval). A `rejected` account can re-register only when username AND email both match the existing row, which resets it to `pending` (clears reason and reviewed_at); any other clash is `409 already_registered`. Login returns 403 `approval_pending` or `registration_rejected` (the latter includes the reason); `get_current_user` (`core/deps.py`) and `/auth/refresh` reject non-approved users. Admins use `GET /api/admin/registrations?status=`, `POST /api/admin/registrations/{id}/approve` and `POST .../reject {reason}` (reason required; a second review is `409 already_reviewed`); `/api/admin/stats` gains `pending_approvals`; the UI is Admin > Approvals. `services/registration_service.py` emails the admin on each new registration (`ADMIN_NOTIFY_EMAIL`, falling back to the first admin user's email) and the applicant on approve/reject (login link built from `FRONTEND_BASE_URL`); emails are best-effort, are logged on failure and never fail the request. Migration `0003_user_approval` adds the three columns and backfills existing users as `approved`.

**Usernames are case-insensitive** for login and sign-up (`func.lower(User.username)` in `routers/auth.py`; the stored casing is what the person typed, and re-apply updates it). Emails are still compared exactly. The DB unique index on `username` is still case-sensitive (no migration), so a concurrent race could in theory create `Bob` and `bob`. Admin login always lands on `/admin` (the Overview) regardless of the page you came from; the Overview always shows a "Pending approvals" tile (even at 0) and the Approvals tab badge refreshes after each decision (via `AdminLayout`'s outlet context `refreshPending`). The site header sits at `z-[55]`, above the chat widget (`z-50`) and below dialogs (`z-[60]`), so the user menu opens over the chat panel.

### Deployment (Render)
`render.yaml` at repo root is a Blueprint: backend deploys from `backend/Dockerfile` on Render's free web-service plan (sleeps after 15 min idle, auto-wakes on next request, URL is permanent regardless), with Postgres as a separate paid `databases:` entry (`toybox-db`, `plan: starter`) wired into `DATABASE_URL` via `fromDatabase` — free-tier Postgres is auto-deleted after 30 days, so this repo is set up assuming the paid DB tier for anything meant to persist. `db/session.py` is already dialect-agnostic (the SQLite `PRAGMA foreign_keys` listener checks the driver module name and no-ops on Postgres), so no code changes are needed to switch `DATABASE_URL` between `sqlite:///` and `postgresql://`. Secrets (`STRIPE_*`, `SMTP_*`, `LYZR_*`, `CORS_ORIGINS`) are marked `sync: false` in the Blueprint — set them in the Render dashboard, never in this file. `ADMIN_NOTIFY_EMAIL` and `FRONTEND_BASE_URL` are NOT in `render.yaml`; add them in the dashboard and redeploy (environment changes only apply on redeploy). `PUBLIC_BASE_URL` is still listed in the Blueprint but no code reads it any more (it only served guest-receipt email images). The Dockerfile's `CMD` and `HEALTHCHECK` bind `${PORT:-8000}` because Render assigns its own port at runtime.
